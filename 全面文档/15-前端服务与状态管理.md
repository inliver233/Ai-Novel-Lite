## 1. API 客户端

**文件**: `frontend/src/services/apiClient.ts`

### 1.1 核心类型定义

```
ApiErrorPayload   = { ok: false; error: { code, message, details? }; request_id }
ApiOkPayload<T>   = { ok: true; data: T; request_id }
ApiRequestInit     = RequestInit & { timeoutMs?: number }
```

所有后端 API 均采用统一的信封格式：成功时 `{ ok: true, data, request_id }`，失败时 `{ ok: false, error, request_id }`。

### 1.2 ApiError 类

继承自 `Error`，包含以下字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | `string` | 错误码，如 `TIMEOUT`、`NETWORK_ERROR`、`BAD_RESPONSE` |
| `requestId` | `string` | 后端返回的请求 ID，用于排障 |
| `details` | `unknown` | 可选的附加错误详情 |
| `status` | `number` | HTTP 状态码（网络错误时为 0） |

### 1.3 超时与取消机制（fetchWithTimeout）

- 默认超时 `DEFAULT_TIMEOUT_MS = 120_000`（2 分钟）
- 内部创建独立的 `AbortController`
- 支持外部传入 `signal`：外部信号 abort 时同步取消内部控制器
- 超时触发时抛出 `code: "TIMEOUT"` 的 `ApiError`
- 用户主动取消（AbortError）时抛出 `code: "REQUEST_ABORTED"`
- 网络异常时抛出 `code: "NETWORK_ERROR"`
- `finally` 块中清理定时器与事件监听

默认 `credentials: "include"`，确保 Cookie 自动携带。

### 1.4 未授权通知（notifyUnauthorized）

通过 `window.dispatchEvent(new CustomEvent("ainovel:unauthorized"))` 广播未授权事件。`AuthContext` 会监听此事件并将用户状态重置为 `unauthenticated`。触发条件由 `shouldNotifyUnauthorized` 策略函数决定。

### 1.5 核心请求方法

#### `apiJson<T>(path, init?): Promise<ApiOkPayload<T>>`

- 自动设置 `Content-Type: application/json`
- 调用 `fetchWithTimeout` 发起请求
- 通过 `parseJsonSafe` 安全解析响应体（空响应返回 `null`，JSON 解析失败返回 `{ _raw: text }`）
- 判断响应是否符合 `ApiOkPayload` / `ApiErrorPayload` 信封格式
- 失败时根据 `shouldNotifyUnauthorized` 决定是否广播未授权事件
- 非标准响应抛出 `code: "BAD_RESPONSE"`

#### `apiDownloadMarkdown(path): Promise<{ filename, content }>`

- 用于下载 Markdown 格式的导出文件
- 检查 `Content-Type` 是否包含 `text/markdown`
- 从 `Content-Disposition` 头解析文件名（支持 `filename*` RFC 5987 编码格式和普通 `filename` 格式）
- 默认文件名回退为 `"ainovel.md"`

#### `apiDownloadAttachment(path): Promise<{ filename, blob, requestId }>`

- 用于下载通用附件（二进制 blob）
- 同样从 `Content-Disposition` 解析文件名
- 成功时返回 `Blob` 对象

### 1.6 文件名安全处理

#### `sanitizeFilename(value): string`

- 取最后一段路径（按 `/` 或 `\` 分割）
- 删除 null 字符（`\0`）
- 将 `\/:*?"<>|` 等 Windows 不安全字符替换为下划线
- 截断到 80 字符

#### `parseContentDispositionFilename(header): string | null`

解析优先级：`filename*`（RFC 5987 编码） > `filename="..."` > `filename=...`

## 6. SSE 客户端

**文件**: `frontend/src/services/sseClient.ts`

### 6.1 SSE 消息类型

```
SSEMessage =
  | { type: "start"; message?; progress?; status?; char_count?; word_count? }
  | { type: "progress"; message; progress; status; char_count?; word_count? }
  | { type: "chunk" | "token"; content: string }
  | { type: "result"; data: unknown }
  | { type: "error"; error: string; code?: number }
  | { type: "done" }
```

### 6.2 SSEClientOptions

```
{
  headers?: Record<string, string>;
  onProgress?: (msg) => void;    // 进度回调
  onChunk?: (content) => void;   // 流式内容块
  onResult?: (data) => void;     // 结构化结果
  onError?: (error, code) => void;
  onDone?: () => void;
  onOpen?: (info: { requestId? }) => void;
}
```

### 6.3 SSEError 类

继承自 `Error`，包含 `code` 和可选 `requestId`。错误码包括：
- `ABORTED`: 用户取消
- `SSE_CONNECTION_ERROR`: 连接失败
- `SSE_BAD_RESPONSE`: HTTP 非 200
- `SSE_PROTOCOL_ERROR`: Content-Type 不是 event-stream
- `SSE_STREAM_ERROR`: 流读取失败
- `SSE_SERVER_ERROR`: 服务端返回 error 事件
- `SSE_EARLY_CLOSE`: 流提前关闭

### 6.4 SSEPostClient 类

核心 SSE 客户端实现，基于 `fetch` + `ReadableStream` 手动解析 SSE 协议：

**构造函数**: `constructor(url, data, options?)`
- `url`: SSE 端点地址
- `data`: POST 请求体（JSON 序列化）
- `options`: 回调与头部配置

**abort()**: 调用内部 `AbortController.abort()` 取消请求

**connect()**: 核心连接方法，返回 `Promise<{ requestId?, result?, accumulatedContent }>`

连接流程：
1. 发起 `POST` 请求（credentials: include，Content-Type: application/json）
2. 检查响应状态码，非 200 时解析错误体并抛出 `ApiError`（含未授权通知逻辑）
3. 验证 Content-Type 必须包含 `text/event-stream`
4. 获取 `ReadableStream.getReader()` 后进入循环读取
5. 使用 `TextDecoder` 解码字节流，以 `\n\n` 分割 SSE 事件块
6. 解析每个块中的 `event:` 和 `data:` 行
7. 根据事件类型（start/progress/chunk/token/result/error/done）分发到对应回调
8. `chunk`/`token` 事件累积到 `accumulatedContent`
9. `result` 事件保存到 `resultData`
10. `done` 事件终止循环并返回结果
11. 容错处理：若代理丢失了终止 done 事件但 result 已到达，仍然正常返回

## 7. 章节数据存储

**文件**: `frontend/src/services/chapterStore.ts`

### 7.1 存储架构概览

`ChapterStore` 是一个独立于 React 的外部数据存储，采用**发布-订阅模式**，通过 `useSyncExternalStore` 与 React 集成。

核心数据结构：
- `metaEntries`: `Map<projectId, CacheEntry<ChapterListItem[]>>` -- 按项目缓存章节元数据列表
- `detailEntries`: `Map<chapterId, CacheEntry<ChapterDetail>>` -- 按章节 ID 缓存详情
- `metaListeners`: `Map<projectId, Set<() => void>>` -- 元数据变更监听器
- `detailListeners`: `Map<chapterId, Set<() => void>>` -- 详情变更监听器
- `chapterProjectIndex`: `Map<chapterId, projectId>` -- 章节到项目的反向索引
- `projectChapterIndex`: `Map<projectId, Set<chapterId>>` -- 项目到章节的正向索引

### 7.2 快照类型（ChapterResourceSnapshot<T>）

```
{
  data: T | null;       // 缓存数据
  error: ApiError | null; // 最近一次错误
  hasLoaded: boolean;   // 是否曾加载成功
  loading: boolean;     // 是否正在加载
  stale: boolean;       // 是否已过期（需要重新加载）
}
```

### 7.3 传输层抽象（ChapterTransport）

定义了可替换的 API 传输接口，默认实现指向 `chaptersApi.ts` 中的函数。测试中可注入 mock 传输层。

### 7.4 缓存策略

- **按需加载**: 首次调用 `loadMeta/loadDetail` 时发起请求
- **命中缓存**: 若 `data` 非空且 `stale === false`，直接返回缓存数据（除非 `force: true`）
- **请求去重**: 同一资源的并发请求共享同一个 `promise`
- **失效机制**: `invalidateProjectChapters`/`invalidateChapterDetail` 将 `stale` 设为 `true`，下次读取时自动刷新
- **级联更新**: 更新章节详情后自动同步更新对应项目的元数据列表（upsertMetaItem）

### 7.5 核心方法

| 方法 | 说明 |
|------|------|
| `loadProjectChapterMeta(projectId, { force? })` | 加载项目的全部章节元数据 |
| `loadChapterDetail(chapterId, { force? })` | 加载单个章节详情 |
| `prefetchChapterDetail(chapterId)` | 静默预取，吞掉错误 |
| `createProjectChapter(projectId, payload)` | 创建章节并更新缓存 |
| `updateChapterDetail(chapterId, payload)` | 更新章节并同步元数据 |
| `deleteProjectChapter(chapterId, { projectId? })` | 删除章节并从缓存中移除 |
| `bulkCreateProjectChapters(projectId, payload, { replace? })` | 批量创建章节；replace=true 时替换项目全部章节缓存 |
| `invalidateProjectChapters(projectId, { dropDetails? })` | 使项目章节缓存失效 |
| `invalidateChapterDetail(chapterId)` | 使单个章节详情缓存失效 |
| `getMetaSnapshot(projectId)` | 获取元数据快照（同步） |
| `getDetailSnapshot(chapterId)` | 获取详情快照（同步） |
| `getKnownProjectId(chapterId)` | 从反向索引查找章节所属项目 |
| `subscribeMeta(projectId, listener)` | 订阅元数据变更，返回取消订阅函数 |
| `subscribeDetail(chapterId, listener)` | 订阅详情变更，返回取消订阅函数 |

### 7.6 全局单例

```typescript
export const chapterStore = createChapterStore();
```

模块导出一个全局单例，所有组件共享同一份缓存。

### 7.7 测试覆盖（chapterStore.test.ts）

4 个测试用例：
1. **缓存命中与强制刷新**: 验证首次加载后缓存命中，invalidate 后重新加载，force 强制加载
2. **详情更新同步元数据**: 更新章节后验证 detail 和 meta 的 has_content/has_summary/status 等标记同步
3. **删除级联清理**: 删除章节后验证 meta 列表和 detail 缓存均清空
4. **批量创建替换**: 批量创建（replace=true）后验证旧章节缓存被清理，新章节正确填充

## 8. 章节标记流解析器

**文件**: `frontend/src/services/chapterMarkerStreamParser.ts`

### 8.1 设计目的

解析 AI 生成的流式文本中的标记分隔符，将流式内容分离为**正文**（content）和**摘要**（summary）两部分。

### 8.2 标记格式

```
<<<CONTENT>>>
...正文内容...
<<<SUMMARY>>>
...摘要内容...
```

标记正则允许宽松匹配：
- `markerContentRe`: `^[ \t]*<<<\s*CONTENT\b\s*(?:>{1,3})?\s*` -- 匹配 `<<<CONTENT>>>`
- `markerSummaryRe`: `^[ \t]*<<<\s*SUMMARY\b\s*(?:>{1,3})?\s*` -- 匹配 `<<<SUMMARY>>>`

### 8.3 解析阶段（ChapterMarkerStreamPhase）

| 阶段 | 说明 |
|------|------|
| `"before"` | 尚未遇到 `<<<CONTENT>>>` 标记 |
| `"content"` | 正在读取正文区域 |
| `"summary"` | 正在读取摘要区域 |
| `"raw"` | 未检测到标记，将全部内容作为正文（回退模式） |

### 8.4 流式缓冲策略

- `maxPreambleChars`（默认 8192）: 在 `before` 阶段如果缓冲超过此长度仍未匹配到标记，切换到 `raw` 模式
- `tailKeepChars`（默认 256）: 在 `content` 阶段，保留缓冲区末尾 256 字节用于跨块标记匹配，其余部分立即输出

这确保了即使标记被拆分到两个 chunk 中，解析器也能正确识别。

### 8.5 API

```
push(chunk: string): ChapterMarkerPushResult    // 输入一个流式块
finalize(): ChapterMarkerPushResult              // 刷新缓冲区中剩余内容
getPhase(): ChapterMarkerStreamPhase             // 当前解析阶段
getBufferLength(): number                        // 当前缓冲区长度
```

`ChapterMarkerPushResult = { phase, contentDelta, summaryDelta }`

### 8.6 测试覆盖（chapterMarkerStreamParser.test.ts）

4 个测试用例：
1. **跨块标记解析**: 标记被拆分到多个 chunk 中，仍能正确解析
2. **空白容差**: 标记周围的空白/缩进不影响解析
3. **无标记回退**: 没有标记时自动切换到 raw 模式，不丢失内容
4. **内存控制**: 10 万字符的长流中缓冲区大小始终不超过 256 字节

## 9. 项目任务运行时

**文件**: `frontend/src/services/projectTaskRuntime.ts`

### 9.1 核心类型

```
ProjectTaskRuntime = {
  run: ProjectTask;                              // 任务主记录
  timeline: ProjectTaskRuntimeEvent[];           // 事件时间线
  checkpoints: ProjectTaskRuntimeCheckpoint[];   // 检查点
  steps: ProjectTaskRuntimeStep[];               // 执行步骤
  artifacts: ProjectTaskRuntimeArtifact[];       // 产出物
  batch: ProjectTaskRuntimeBatch | null;         // 批量生成任务引用
}
```

**ProjectTaskRuntimeEvent**: 包含 `seq`（序号）、`event_type`、`created_at`、`source`、`reason`、`checkpoint`、`step`、`error`、`result` 字段。

## 10. 项目任务存储

### 10.1 存储架构

与 `chapterStore` 采用完全相同的架构模式，独立于 React 的外部存储 + 发布订阅。

## 14. 向导服务

**文件**: `frontend/src/services/wizard.ts`

### 14.1 向导步骤定义

8 个固定步骤，按创作流程排列：

| 步骤键 | 标题 | 权重 | 完成条件 |
|--------|------|------|----------|
| `settings` | 补齐设定 | 6 | 世界观/风格/约束/类型/梗概任一非空 |

| `writing` | 完成全部章节 | 36 | 全部章节状态为 done |

### 14.2 步骤状态

```
WizardStepState = "todo" | "done" | "skipped"
```

用户可手动跳过步骤（存储在 localStorage）。

### 14.3 进度百分比计算

```
percent = sum(weights[step.key] * stepProgress(step.key, step.state))
```

- done/skipped 步骤：progress = 1
- writing 步骤：progress = doneChapters / totalChapters（部分完成）
- 其他 todo 步骤：progress = 0
- 结果钳制在 [0, 100] 范围

### 14.4 事件通知机制

通过 `CustomEvent("ainovel:wizard:progress_invalidated")` 广播进度变更事件。

失效原因（reason）：
- `project_changed`: 项目数据变更（触发刷新）
- `skip_changed`: 跳过状态变更
- `llm_test_ok`: LLM 测试通过
- `preview_seen`: 预览页已访问
- `exported`: 导出完成

### 14.5 localStorage 状态管理

| 函数 | 说明 |
|------|------|
| `isWizardStepSkipped(projectId, step)` | 查询步骤是否被跳过 |

| `markWizardLlmTestOk(projectId, provider, model)` | 记录 LLM 测试通过 |

| `markWizardExported(projectId)` | 记录导出时间 |
| `hasWizardExported(projectId)` / `getWizardExportedAt(projectId)` | 查询导出状态/时间 |
| `markWizardProjectChanged(projectId)` | 记录项目变更时间 |

## 15. 未授权策略

**文件**: `frontend/src/services/unauthorizedPolicy.ts`

### 15.1 策略函数

```typescript
shouldNotifyUnauthorized(status: number, errorCode?: string | null): boolean
```

逻辑：
1. 非 401 状态码 -> 返回 `false`（不通知）
2. 401 + 无错误码 -> 返回 `true`（保守策略，未知 401 默认通知）

4. 401 + 其他错误码（如 `LLM_AUTH_ERROR`、`LLM_KEY_MISSING`）-> 返回 `false`

### 15.2 设计意图

## 16. React Context 详解

### 16.1 认证上下文

#### auth.ts -- Context 定义

**AuthUser 类型**:
```
{ id: string; displayName: string; isAdmin: boolean }
```

**AuthSession 类型**:
```
{ expireAt: number | null }   // Unix 秒级时间戳
```

**AuthStatus 枚举**:
```
"loading" | "authenticated" | "dev_fallback" | "unauthenticated"
```

- `loading`: 初始状态，正在获取用户信息
- `authenticated`: 已认证（正式登录）
- `dev_fallback`: 开发模式回退（未登录但后端可访问）
- `unauthenticated`: 未认证（需要登录）

**AuthApi 类型** -- Context 提供的完整接口：
```
AuthState & {
  refresh: (opts?: { silent?: boolean }) => Promise<void>;
  login: (args: { userId, password }) => Promise<void>;
  register: (args: { userId, password, displayName?, email? }) => Promise<void>;
  logout: () => Promise<void>;
}
```

**useAuth() Hook**: 从 Context 获取 AuthApi，未在 Provider 内调用时抛出异常。

#### Token 刷新调度算法（computeNextAuthRefreshDelayMs）

参数：`{ expireAtSec: number | null; nowMs?: number }`

常量：
- `defaultDelayMs = 5 * 60_000`（5 分钟）: expireAtSec 为 null 或非有限数时的默认刷新间隔
- `minDelayMs = 30_000`（30 秒）: 最小刷新间隔
- `clockSkewGuardSec = 60`（1 分钟）: 时钟偏差保护
- `maxLeadSec = 5 * 60`（5 分钟）: 最大提前量
- `minLeadSec = 30`（30 秒）: 最小提前量
- `leadFraction = 0.2`: 剩余时间的 20% 作为提前量
- `maxTimeoutDelayMs = 2_000_000_000`: 防止 setTimeout 溢出

算法：
1. 计算剩余时间 `remainingSec = expireAtSec - (nowSec + clockSkewGuardSec)`
2. 计算提前量 `leadSec = clamp(remainingSec * 0.2, 30, 300)`
3. 目标延迟 `targetDelayMs = (remainingSec - leadSec) * 1000`
4. 结果钳制在 `[30s, 2000000000ms]` 范围

测试覆盖（authRefreshSchedule.test.ts）：6 个用例覆盖 null/远未来/临近/过期/非有限数/超大值场景。

#### AuthContext.tsx -- Provider 实现

**AuthProvider 组件**:

状态管理：
- `state`: `AuthState`（status + user + session）
- `statusRef`: 通过 ref 跟踪最新状态，供事件处理器使用
- `sessionExpireAtRef`: 跟踪最新过期时间，供刷新调度使用

核心方法：

**refresh({ silent? })**:
1. 调用 `GET /api/auth/user`
2. 成功：映射用户信息并设置为 `authenticated`
3. 401 + 开发模式（`VITE_DEV_FALLBACK_ENABLED`）：尝试调用 `/api/projects` 验证后端可访问性
   - 可访问：设置为 `dev_fallback`，用户为 `{ id: "local-user", displayName: "本地用户" }`
   - 不可访问：设置为 `unauthenticated`
4. 其他错误：设置为 `unauthenticated`

**refreshSession()**:
1. 调用 `POST /api/auth/refresh`
2. 成功：更新 session.expireAt
3. 401：设置为 `unauthenticated`

**login({ userId, password })**:
- 调用 `POST /api/auth/local/login`

**register({ userId, password, displayName?, email? })**:
- 调用 `POST /api/auth/local/register`

**logout()**:
- 调用 `POST /api/auth/logout`（忽略错误）
- 清除 currentUserId
- 静默刷新

副作用：
1. 挂载时自动调用 `refresh()`
2. 监听 `ainovel:unauthorized` 事件，收到时将状态设为 `unauthenticated`
3. 状态为 `authenticated` 时启动定时刷新调度：
   - 使用 `computeNextAuthRefreshDelayMs` 计算下次刷新延迟
   - 刷新完成后递归调度下一次
   - 组件卸载或状态非 authenticated 时取消
